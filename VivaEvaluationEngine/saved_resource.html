Architecture Review · R26-SE-025

VivaEvaluationEngine

A full technical audit of the video–audio viva grading engine: what it does, how it is built, what is sound, and where it is measuring something other than what it reports.

Branch feat-viva-fix Scope 20 modules · 8 services Weights 49 MB in-tree Tests 0 First pass 2026-08-09 Re-audit 2026-08-12
Executive verdict · re-audit

Since the first pass, real engineering happened: extract_features.py and extract_emotion.py were rewritten to do genuine librosa-based pitch/tempo extraction instead of returning hard-coded zeros, requirements.txt was pinned and trimmed, Whisper output moved off a tracked path in the working directory and got cached, and the divergent second grading orchestrator was deleted outright. MongoDB persistence was added cleanly. This is a team that responds to findings — four of the original nineteen are now resolved.

But the two defects that change marks were not touched, and this pass reproduced them live rather than from old committed data. A fresh 30-second recording of coherent, articulate speech about vocal technique was run through the current pipeline end-to-end during this audit: it scored articulation_score: 0.0, the mathematical floor, and its engagement scores landed on exactly the same three quantized values as before — 0.4, 0.75, 0.95 — proving the confidence-weighted blend is still discarded on every single frame, not an edge case.

Two new findings surfaced outside the engine itself: the client's viva grading panel that a lecturer actually acts on is hardcoded mock data, disconnected from the real scores displayed one panel over; and the current requirements file has drifted ahead of what's actually installed, which would fail a fresh checkout today.

01 · System

What the engine actually does

It ingests one viva recording and returns a JSON verdict containing a per-frame timeline, a confidence_score (0–100), an engagement_score (0–100) and an audio_grade (0–10). Two independent pipelines run over the same file and their results are merged by whichever caller invoked them.

02 · Critical

Defects that produce wrong marks

Each of these changes the number a student receives. The first three are reproduced against the committed sample output rather than argued from the source.

V-01

Speech emotion is a keyword/pitch heuristic reported with model-grade confidence

Reproduced liveCritical
extract_emotion.py (rewritten) | services/viva_analysis.py:56–106

Reframed since 08-09: extract_emotion.py no longer calls a real speech-emotion model at all — it was rewritten to a pitch/RMS threshold heuristic, and to its credit the new code says so in its own comment ("Lightweight heuristic emotion estimator used when no dedicated speech-emotion model is wired"). That's more honest internally. But the API contract didn't change: it still returns a confidence field indistinguishable from a real model's, and viva_analysis.py's older _fallback_audio_emotion is still there as a second layer if the first heuristic returns nothing — two heuristics deep, one field name.

Live evidence from this pass: a calm, instructional 30-second recording about vocal technique — the speaker explicitly discussing monotone vs. expressive delivery, not expressing surprise — was classified:

Fresh run, this audit, VivaEvaluationEngine/videos/video_test-01.mp4: transcript (real, Whisper-transcribed): "...Instead of speaking monotone like this, what am I going to speak about today?... Monotone is boring. So how do we take your voice to the next level?..." audio_emotion.predicted_emotion = "surprise" audio_emotion.confidence = 0.857 (85.7%) why: pitch_std 70.29 > 45 and rms 0.074 > 0.04 → hits the heuristic's hard-coded "surprise" branch (the speaker's pitch varies *because* they're demonstrating expressive delivery, not because they're surprised)

A downstream marker sees a confident machine judgement where there is a pitch-variance threshold that fires on the exact kind of expressive, varied delivery an examiner would normally reward.

Fix Add source: "heuristic" to the field and cap heuristic confidence well below what a trained model would report (~0.4 ceiling, as the code already does elsewhere for its other fallback). Consider whether reporting a specific emotion label at all is warranted without a trained acoustic model backing it.
V-02

Articulation scoring is inverted: healthy speech scores 0, failed extraction scores 1

Reproduced liveCritical
services/viva_analysis.py:127 (unchanged since 08-09)

The jitter coefficient of 120 saturates the term at jitter values well inside the normal range for human voice, so real measurements floor the score; only an all-zero feature vector — that is, a failed extraction — reaches the maximum. This formula is byte-identical to the version reviewed on 08-09; it was not part of the audio-feature rewrite.

articulation = 1.0 - clamp((jitter*120 + shimmer*12) / 2) Fresh run, this audit (real speech, real librosa measurement, NOT a failed extraction): jitter_local = 0.023656 shimmer_local = 0.15271 (0.023656*120 + 0.15271*12) / 2 = (2.839 + 1.833)/2 = 2.34 → clamped to 1.0 articulation_score = 1.0 - 1.0 = 0.0 Result: audio_grade = 4.93/10 for a clear, coherent, 78-word articulate speech sample about vocal delivery technique — dragged down entirely by a term that can never score above ~0.3 for any human voice, healthy or not. a failed Parselmouth run (all features default to 0.0): (0*120 + 0*12)/2 = 0 → articulation = 1.0 The 0.16-weighted "articulation" term rewards absence of data and penalises its presence, confirmed on two independent samples three days apart.
Fix Recalibrate against published jitter/shimmer norms (jitter ~0.5–2%, shimmer ~3–10%), and make an unmeasurable feature return None rather than 0.0 so it can be excluded from the weighted sum instead of scoring in it.
V-03

Missing data pays out marks; a silent video scores 3.0/10

ProvenCritical
services/viva_analysis.py:103–164

Two of the eight grade components are expressed as 1.0 - penalty. With no data the penalty is zero, so they pay full marks. Together they are 30% of the grade.

Reproducing _score_audio_grade at the failure boundary: SCENARIO pitch stab clar artic → grade Parselmouth fails entirely 0.000 1.000 0.000 1.000 → 3.50/10 Completely silent video 0.000 1.000 0.000 1.000 → 3.00/10 Healthy measured speech 1.000 0.667 0.600 0.040 → 6.38/10 A student who says nothing, or whose audio fails to process, receives 30-35% rather than a refusal to grade.
Fix Gate the grade on a data-sufficiency check — voiced-frame count, duration, transcript length. Below threshold, return status:"insufficient_audio" with no numeric grade rather than a floor score.
V-04

anger falls through every scoring bucket

Critical
config.py:8–20 vs services/emotion_detector.py:25–34

The classifier emits anger. The taxonomy in config.py lists angry, and EMOTION_ALIASES reconciles happiness and surprised but not this pair. Anger therefore matches no bucket in either build_summary or compute_confidence_score, while still counting in the denominator.

Model CLASS_NAMES → canonical → bucket Neutral → neutral → NEUTRAL Happy → happy → POSITIVE Sad → sad → NEGATIVE Surprise → surprise → SURPRISE Fear → fear → NEGATIVE Disgust → disgust → NEGATIVE Anger → anger → *** FALLS THROUGH ALL BUCKETS *** Contempt → contempt → NEGATIVE Consequences: - summary ratios silently stop summing to 1.0 - negative_ratio understated → the ">0.4 → x0.7" confidence penalty (scoring.py:69) can fail to trigger - a visibly angry candidate scores higher than an equally negative but "sad"-classified one
Fix Add "anger": "angry" to EMOTION_ALIASES, then add a startup assertion that every model class canonicalises into exactly one bucket. This class of bug should fail at import, not at grading time.
V-05

Frames with no detected face are deleted, leaving no coverage metric

Critical
services/analysis_service.py:142–149

No-face frames are carefully constructed with valid:False … and then filtered out before the response is built. The returned timeline contains only surviving frames, and no field records how many were discarded.

clean_pairs = [(t,g) for t,g in paired if t["valid"] is True] response = {"timeline": smoothed_timeline, ...} # valid frames only → a 10-minute viva in which the face was found in 8 frames is byte-for-byte indistinguishable from an 8-second viva analysed perfectly. Both return 8 entries, all valid:true. The committed sample has exactly 8 entries at t=0..7. Nothing in the file can tell you which case it is.

Scores computed from a handful of frames are presented with the same authority as scores from hundreds. This removes the reviewer's ability to distrust a result.

Fix Return frames_sampled, frames_with_face and a derived coverage ratio; refuse to emit scores below a coverage floor.
03 · High

Correctness and reliability

V-06

Engagement confidence blending is computed, then discarded

Reproduced liveHigh
services/engagement_detector.py:98 vs :167–169 (unchanged since 08-09)

EngagementRecognizer.predict derives a confidence-weighted score, shrinking toward 0.5 when the model is unsure. The wrapper's tuple-parsing branch then returns a flat table lookup instead, so that third element is never read.

produced blended = (level*conf) + (0.5*(1-conf)) discarded return ..., ENGAGEMENT_LEVEL_SCORES.get(label, 0.5) Verified twice now, three days apart. Fresh run this audit, 30 frames, all engagement_model_score values across the run: label counts: low=12, high=16, very_high=2 distinct engagement_model_score values = [0.4, 0.75, 0.95] Exactly ENGAGEMENT_LEVEL_SCORES = {low:0.40, high:0.75, very_high:0.95}. Zero variance within any label across 30 independent frames with different confidences — if the blend ran, no two frames would plausibly land on the identical float.
Fix Return the blended value from _parse_prediction's string branch. The defensive multi-shape parser is unnecessary for a model this code owns — deleting it removes the bug outright.
N-01

The lecturer-facing grading panel is entirely disconnected from the AI results shown next to it

New this passCritical
Gradex_AI_Client/src/app/components/VivaPage.tsx:12–17, 628–668

This sits outside the engine itself, in the client that consumes it — but it undermines everything above just as effectively. The page's upper panels (confidence score, engagement score, audio grade, transcript, timeline) are genuinely wired to /api/viva-analyze's real response. The "Evaluation rubric" panel a lecturer would actually act on is a hardcoded constant that never reads analysisResult at all.

const criteria = [ { name: "Communication Skills", score: 8, max: 10 }, { name: "Technical Knowledge", score: 7, max: 10 }, { name: "Problem-Solving", score: 9, max: 10 }, { name: "Presentation Quality", score: 7, max: 10 }, ]; // ^ identical for every video, every student, every run. // total/max below are derived from this constant, never from // confidence_score, engagement_score, or audio_grade. // grade always starts at "A" ...Distinction // always shown // no onClick handler at all

A lecturer can watch a real, badly-scoring analysis (e.g. the 4.93/10 audio grade reproduced under V‑02) and the panel beside it will still show 31/40 marks defaulting to grade "A" with a "Distinction" badge, tied to a Save & publish button that does nothing when clicked. N-02

The committed requirements.txt is ahead of what's actually installed

New this passHigh
VivaEvaluationEngine/requirements.txt vs. project venv

The 08-12 rewrite added a real dependency on librosa (plus torchaudio, soundfile it pulls in). The file correctly lists and pins all three. But this audit found none of them installed in the project's own .venv — importing the engine failed with ModuleNotFoundError: No module named 'librosa' on first attempt.

$ python -c "from Gradex_AI_Server.app.viva_service import analyze_video_file" ModuleNotFoundError: No module named 'librosa' venv audit at time of this review: torchaudio MISSING librosa MISSING soundfile MISSING (9 others) OK → a fresh `git pull` + existing venv, with no re-install step, cannot run the audio pipeline at all right now.

Not a code defect — a process gap. Whoever is running this locally either has a second, separately-provisioned environment, or hasn't re-run pip install since the rewrite landed. Either way, nothing in the repo enforces or even flags the drift.

Fix No code change needed, just discipline: pip install -r VivaEvaluationEngine/requirements.txt after every pull that touches it, and consider a CI smoke test that just imports the package to catch exactly this before it reaches a teammate.
V-07

Anger and contempt score higher than sadness on engagement

High
services/scoring.py:85–93

The emotion_map omits both anger (spelling drift again) and contempt (never listed). Both resolve to the 0.5 default, which sits above every genuinely negative weight.

neutral 1.0 happy 0.9 surprise 0.6 sad 0.3 fear 0.2 disgust 0.1 anger 0.5 ← default contempt 0.5 ← default An angry candidate is scored as more engaged than a sad one, and 5x more engaged than a disgusted one.
Fix Complete the map and replace .get(label, 0.5) with a lookup that raises on an unknown label.
V-08

Roughly 60 “features” are hard-coded zeros presented as measurements

Fixed since 08-09
extract_features.py (rewritten)

extract_features.py was rewritten to actually call librosa.load, librosa.yin for real pitch tracking, and librosa.beat.beat_track for real tempo. Verified this pass: the fresh test run returned tempo_bpm: 104.17 and pitch_mean_hz: 153.26 — genuine measurements, not the constant zero this finding originally flagged. MFCC/chroma/spectral-rolloff were dropped entirely rather than kept as fake zeros, which is the right call: an honestly smaller feature set beats a padded, fake one.

Remaining gap START_HERE.md and the other status docs were written for the old implementation and haven't been revisited; they still describe the pre-rewrite feature set. Low-priority doc cleanup, not a code defect.
V-09

Silent-zero fallback on extraction failure, now via broad except Exception

Partially fixedMedium
extract_features.py: _safe_pitch_stats, _safe_voice_quality

Improved, not resolved. The rewrite consolidated eleven separate bare except: blocks (the original finding) into two functions, each with a single except Exception: — a real fix for the bare-except / KeyboardInterrupt-swallowing problem. But the underlying pattern is unchanged: any failure in pitch tracking or Praat's jitter/shimmer/HNR calls still silently returns all-zero dicts, indistinguishable from a genuinely silent or perfectly clean voice, and per V‑02/V‑03 zero remains a high-scoring input.

Fix Downgraded from High to Medium given the exception-handling improvement. Still needs: record None plus a features_failed list rather than zeros, so callers can distinguish "measured zero" from "extraction failed."
V-10

Audio valence mapping bypasses the canonicaliser

High
services/viva_analysis.py:39–47

_emotion_valence re-implements label matching with its own hardcoded literal sets instead of calling canonical_emotion_label. Any label variant the upstream model actually emits — surprised, fearful, happiness — misses the positive and negative sets and silently degrades to "neutral".

if normalized in {"happy","surprise"}: → positive if normalized in {"sad","angry","fear","disgust","contempt"}: → negative if normalized: → neutral ← catch-all config.py already aliases "surprised"→"surprise" and "happiness"→"happy", proving the codebase knows these variants occur — this function just never asks. Neutral valence pays 0.75*conf+0.15; negative pays 0.45*conf+0.05. A misrouted negative emotion is worth up to 0.35 more grade weight.
Fix Route every label through canonical_emotion_label and share one taxonomy between the audio and video paths.
V-11

The analysis blocks the server's event loop

High
Gradex_AI_Server/app/main.py → viva_service.analyze_video_file

An async def handler calls the fully synchronous, CPU-bound analyze_video_file directly. For the entire duration of a viva analysis — two full video decodes plus hundreds of forward passes — the whole FastAPI process serves nothing else, including health checks.

@app.post("/api/viva-analyze") async def viva_analyze(video: UploadFile = File(...)): result = analyze_video_file(str(file_path), debug=False) # blocking
Fix Minimum: await run_in_threadpool(...). Correct: move to a job queue returning a task id, since these runs are minutes long and the client currently holds an open HTTP connection throughout.
V-12

Confidence scoring ignores the model's own certainty

High
services/scoring.py:39–73

compute_confidence_score counts label categories only. A happy prediction at 0.26 certainty contributes exactly as much as one at 0.99, even though emotion_confidence is carried through the timeline and is available at that point.

In the committed sample, emotion_confidence ranges 0.51-0.79 but the reported confidence_score of 87.5 is computed purely from the 7:1 positive-to-neutral label ratio.
Fix Weight each frame by its confidence, or discard frames below a floor before counting.
04 · Medium

Design and maintainability

V-13

Smoothing bridges across time gaps

Medium
services/scoring.py:15–36

Majority-vote smoothing runs after invalid frames are removed, so entries that were seconds or minutes apart become window neighbours. The window also averages confidence while keeping the voted label, so the reported confidence can belong to a different emotion than the one beside it.

Fix Smooth on the time axis, not the array index, and recompute confidence for the winning label only.
V-14

“Yaw” and “pitch” are face width and height

Medium
services/gaze_head_analyser.py:52–56

These are normalised landmark distances, not angles. Both shrink when the subject sits further from the camera, so head_stability — 1.0 - std(yaw)*10 with an unexplained factor of 10 — conflates head movement with distance change. pitch is computed on every frame and never read.

def _head_yaw(lm): return abs(lm[234].x - lm[454].x) # cheek-to-cheek def _head_pitch(lm): return abs(lm[1].y - lm[152].y) # nose-to-chin
Fix Use solvePnP for real Euler angles, or normalise by inter-ocular distance and rename to face_width_ratio. Delete the unused pitch computation.
V-15

Configuration fields that silently do nothing

Medium
config.py:39, :63–65

AppConfig.positive_emotions, neutral_emotions and surprise_emotions are never read — analysis_service imports the module-level constants instead. Overriding them has no effect. NEUTRAL_WEIGHT = 0.5 is likewise unused; scoring.py hardcodes 0.6 for neutral.

Fix Read from the config object, or delete the fields. A config knob that appears to work and doesn't is worse than none.

V-18

Blink rate skews with sampling-step rounding

Medium
services/blink_sampler.py:68

Duration is inferred from the sample count and the requested rate rather than the video clock. When source_fps / sample_fps does not divide evenly, the estimate drifts — at 25 fps the step rounds 2.5→2, overstating duration by 25% and understating blinks/minute proportionally. That error then feeds the engagement blend.

Fix Compute duration from CAP_PROP_FRAME_COUNT / source_fps.
V-19

The package cannot be imported as a package

Medium
__init__.py:7, services/*.py

Every internal import is absolute (from services.x import y, from config import ...), so the directory itself must be on sys.path. import VivaEvaluationEngine fails; the server works around this by injecting the path at runtime, and by passing absolute model paths because the relative defaults break under a different CWD.

viva_service.py: sys.path.insert(0, str(VIVA_ENGINE_ROOT)) # required workaround emotion_model_abs = str(VIVA_ENGINE_ROOT / "models" / ...)
Fix Convert to relative imports (from .services.x import y) and resolve model defaults against Path(__file__).parent. Then the sys.path hack and the absolute-path plumbing both disappear.
05 · Performance

Cost profile

The engine decodes each video twice and runs every inference at batch size one. Model weights are loaded from disk on every request rather than once per process.

IssueWhereCost for a 5-min 30 fps viva
Second full decode for blinksblink_sampler.py:249,000 frames decoded twice
static_image_mode=True disables landmark tracking, forcing full detection per frameblink_sampler.py:29–34~3,000 FaceMesh detections
Batch-size-1 inference, no GPU batchingemotion/engagement_detector~600 separate forward passes
Whisper reloaded per calltranscribe.py:19~140 MB load, every request
wav2vec2 from_pretrained inside the functionextract_emotion.py:14–15Large XLSR checkpoint re-instantiated per call
Formants sampled in a Python loop at 10 msextract_features.py:104–113~3 Praat calls × 100/sec of audio

Blink sampling alone accounts for roughly ten times the face-analysis work of the main pipeline, to produce a single scalar carrying 10% of one score. Sampling it at 1–2 fps inside the existing decode loop would remove most of the engine's runtime.

06 · Supply chain

Security and reproducibility

S-01

Pickle deserialisation of in-tree weights

High
emotion_detector.py:63, engagement_detector.py:53

torch.load(..., weights_only=False) executes arbitrary code during unpickling. The three checkpoints are committed binaries with no recorded provenance, no training script in this directory, no dataset reference and no evaluation metrics — so their contents cannot be audited or reproduced.

Fix Re-save as state_dict and load with weights_only=True; record training provenance and a checksum.
  • S-02 — Runtime downloads. face_detector.py:58 fetches a .tflite from a Google CDN on first run; extract_emotion.py pulls from the HuggingFace Hub. Both are unpinned and unverified, and both make the engine fail on an offline or restricted host.
  • S-03 — Fixed since 08-09 Version pins. requirements.txt was rewritten with real range pins (torch>=2.4,<3 etc.) across all 12 entries. The torch.library.register_fake shim this drift originally caused is still in the code as a scar, but the drift itself is fixed.
  • S-04 — 49 MB of weights in git, no LFS. Still open. Three ~16 MB .pt files are committed directly. enet_b0_8_best_afew.pt is loaded by nothing — 16 MB of dead weight in every clone, forever, since git history is append-only.
  • S-05 — Fixed since 08-09 Unused dependencies. The old 20-entry list with 11 unused packages is gone. The rewritten requirements.txt has 12 entries; every one of them is now genuinely imported somewhere in the tree, verified this pass. The flip side is N‑02 above: pinned-and-used is only half the story if the venv running the code hasn't caught up to the file.
07 · Process

Testing, observability, documentation

  • No tests of any kind. There is no pytest suite, no fixture video, no golden-output comparison. Every defect above would have been caught by a single test asserting that each model class maps to a scoring bucket, or that a zero-feature vector does not score 3.5/10.
  • Observability is print(). No logging module, no levels, no structured context. The server-side [VIVA] timing lines are the only operational signal, and the silent fallbacks (V‑01, V‑09) produce no output at all — the failures that matter most are the quietest.
  • Documentation overstates the system, and is now further out of date. START_HERE.md is titled “PROJECT COMPLETED SUCCESSFULLY”, marked “Production Ready”, and describes the pre-08-12 feature set (still claims the old wav2vec2 emotion model, doesn't mention MongoDB persistence, references a script that's since been deleted). Nothing in the docs was touched by the rewrite that changed the code underneath them.
  • Dead surface. examples.py (built for the deleted audio_analyzer.py orchestrator, so at least some of its examples no longer match anything), the unused third checkpoint, the unread pitch signal.
08 · Credit

What is genuinely well built

The structural work here is better than the scoring work, and it is what makes the defects above cheap to fix. Nothing in this review requires a rewrite — and the 08-09→08-12 delta above is direct evidence of that: four real fixes landed in three days without touching the module boundaries.

  • The team responds to findings, and responds correctly. Every one of the four fixes in the delta section addressed the actual root cause, not a surface patch: real librosa calls instead of deleting the zero-stuffing, an explicit output path instead of a workaround, deletion instead of a compatibility shim. That's the harder, better fix in each case.
  • MongoDB persistence is wired cleanly. The new app/core/database.py lifespan hook, connect/disconnect on startup/shutdown, and a best-effort insert that logs a warning rather than failing an otherwise-successful analysis if the write fails — correct failure-isolation instinct for a persistence layer bolted onto an existing endpoint.
  • Clean single-responsibility services. Frame supply, face detection, emotion, engagement, gaze, blink and scoring are each one module with one job and no cross-talk. This is why V‑06, V‑07 and V‑12 are one-file fixes.
  • Resource lifetimes are handled correctly. GazeHeadAnalyser and FaceDetector are context managers; VideoProcessor releases its capture in finally; viva_analysis removes its temp WAV in finally even on failure. MediaPipe and OpenCV handles are not leaked.
  • Deliberate runtime-compatibility handling. The dual MediaPipe path (solutions API with a Tasks-API fallback) and the torch.library shim show real deployment experience — someone hit these in the field and handled them.
  • Scoring is explainable. grade_breakdown exposes all eight components rather than emitting a bare number. That transparency is exactly what let this review verify the maths from the output file, and it is the right instinct for a system that grades people.
  • A canonicalisation layer exists. canonical_emotion_label / canonical_engagement_label are the correct answer to label drift. The defects are gaps in the table, not a missing concept.
  • Typed, readable code. Type hints throughout, dataclasses for config and frames, no god-objects, functions that fit on a screen.
  • Sensible integration boundary. The server injecting absolute model paths so the engine works under a different CWD is a thoughtful accommodation of V‑19 rather than a hack.
  • Temporal smoothing is the right idea. Majority-vote over a window is appropriate for jittery per-frame classification — it just needs to respect time (V‑13).
  • Multi-signal fusion is the right design. Blending emotion, gaze, head stability, blink rate and a model score is a defensible approach to engagement. The architecture is sound; the coefficients are unvalidated.
